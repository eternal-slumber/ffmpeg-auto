# Content Factory: устройство проекта и журнал разработки

Этот файл — живая документация проекта. После каждого этапа здесь фиксируются
цель, поток данных, ответственность функций, проверки и следующий шаг.

## Текущее состояние

Готовы этапы 0–6 и минимальный debug UI:

1. доказан FFmpeg pipeline с остановкой исходника и chroma key баннера;
2. Go-приложение получает метаданные source и banner через `ffprobe`;
3. исходная длительность делится на равные `ClipPlan`;
4. для каждого клипа рассчитываются точки вставки баннера.
5. каждый `ClipPlan` рендерится в самостоятельный MP4 и проверяется через
   `ffprobe`.
6. видео приводится к вертикальному `1080×1920` без растяжения исходного кадра.
7. banner вставляется с chroma key, freeze-frame и собственной аудиодорожкой,
   после чего source продолжается с прежней позиции.
8. локальный debug UI запускает тот же pipeline, показывает ClipPlan и
   воспроизводит все готовые ролики в браузере.

CLI выводит JSON, а debug UI даёт форму запуска, таблицу плана и video preview.

## Запуск

Требования:

- Go 1.22 или новее;
- `ffprobe` и `ffmpeg` в системном `PATH`;
- macOS или Linux.

Из корня проекта:

```sh
go test ./...
go vet ./...
go run ./cmd/api
go run ./cmd/web
```

Полная форма команды:

```sh
go run ./cmd/api /path/to/source.mp4 10 /path/to/banner.mp4 /path/to/output.mp4
```

Если аргументы не указаны, используются:

```text
source: storage/incoming/source.mp4
parts:  10
banner: storage/incoming/banner.mp4
output: storage/output/clip-001.mp4
```

## Полный поток данных под капотом

```text
CLI arguments
    ↓
cmd/api/main.go
    ↓
FFProbe.Probe(source)
    ↓
exec.CommandContext → ffprobe → JSON
    ↓
parseProbeOutput
    ↓
source MediaMetadata
    ↓
FFProbe.Probe(banner)
    ↓
banner MediaMetadata
    ↓
EqualSplit(source.Duration, parts)
    ↓
ClipPlan[]
    ↓
PlanInterruptions(clip.Duration, banner.Duration)
    ↓
каждый ClipPlan получает Interruption[]
    ↓
для каждого ClipPlan по очереди:
    ↓
FFmpeg.Render(source, banner, clip)
    ↓
exec.CommandContext → ffmpeg → clip-NNN.mp4
    ↓
FFProbe.Probe(clip-NNN.mp4)
    ↓
encoding/json → stdout
```

Debug UI вызывает тот же `factory.Run`, но выводит результат через HTML:

```text
Browser form
    ↓
POST /render
    ↓
resolveMedia + parts validation
    ↓
factory.Run (тот же pipeline, что у CLI)
    ↓
HTML metadata + ClipPlan table + JSON + video preview
```

JSON содержит декларативный план, пути результатов и метаданные каждого
проверенного выходного файла. Renderer применяет рассчитанные `Interruption[]` без знания
правил, по которым они появились.

## Этап 0 — Technical spike

Цель этапа — проверить самый рискованный участок до написания backend.

Вручную был проверен единый FFmpeg pipeline:

```text
source
→ вертикальная композиция
→ остановка video и audio
→ freeze frame
→ удаление зелёного фона banner
→ overlay и banner audio
→ продолжение source с прежней позиции
→ MP4
```

Результат находится в `content-factory-spike/final-test.mp4`. Этот эксперимент
доказал техническую осуществимость, но его команда ещё не перенесена в Go.

## Этап 1 — Media Probe

### `model.MediaMetadata`

Единый результат анализа любого медиафайла:

- `Duration` — длительность в секундах;
- `Width`, `Height` — размер первого видеопотока;
- `FPS` — частота кадров;
- `VideoCodec`, `AudioCodec` — имена кодеков;
- `HasVideo`, `HasAudio` — наличие потоков.

Модель ничего не знает о FFmpeg и может использоваться планировщиками,
renderer или будущим HTTP API.

### `media.Prober`

Интерфейс задаёт контракт:

```go
Probe(context.Context, path) (MediaMetadata, error)
```

Контекст позволяет отменить внешний процесс. Путь передаётся отдельным
аргументом, а не частью shell-команды.

### `media.FFProbe.Probe`

Метод выбирает executable: значение `FFProbe.Command` либо `ffprobe` из
`PATH`. Затем `exec.CommandContext` запускает программу с `-of json` и
запрашивает только нужные поля.

`CombinedOutput` сохраняет диагностический текст при ошибке. При успехе байты
передаются в `parseProbeOutput`.

### `parseProbeOutput`

Функция:

1. декодирует JSON во внутреннюю структуру `probeOutput`;
2. переводит строковую длительность в `float64`;
3. находит первый video stream;
4. находит первый audio stream;
5. получает номинальный FPS из `r_frame_rate`, а при его отсутствии — из
   `avg_frame_rate`;
6. возвращает `MediaMetadata`.

### `parseRate`

FFprobe отдаёт FPS как дробь, например `30000/1001`. Функция разбирает
числитель и знаменатель, запрещает деление на ноль и возвращает `29.97...`.
`r_frame_rate` выбран первым, потому что `avg_frame_rate` может немного
отклоняться из-за длительности последнего кадра: у текущего 60 FPS source он
равен `60.023...`, хотя номинальная кадровая сетка равна ровно `60`.

## Этап 2 — Equal Split Planner

### `model.ClipPlan`

`ClipPlan` описывает будущий ролик:

- `Number` — номер с единицы;
- `Start` — начало в source;
- `Duration` — сколько исходного контента использовать;
- `Interruptions` — рассчитанные на этапе 3 вставки.

### `planner.EqualSplit`

Вход:

```text
source duration + number of parts
```

Выход:

```text
[]ClipPlan
```

Функция отклоняет нулевую, отрицательную, бесконечную и `NaN` длительность,
а также неположительное число частей.

Для каждого клипа границы считаются от полной длительности:

```text
start = duration × i / parts
end   = duration × (i + 1) / parts
```

Продолжительности предыдущих клипов не складываются, поэтому ошибка округления
не накапливается. Конец последнего клипа явно приравнивается к концу source.

## Этап 3 — Interruption Planner

### `model.Interruption`

Одна вставка содержит:

- `At` — позицию относительно исходного контента конкретного клипа;
- `Duration` — фактическую длительность banner из `ffprobe`.

Позиции не включают длительность предыдущих баннеров. Например, точки `30` и
`60` означают 30 и 60 секунд source-контента, даже если первая вставка удлинила
готовый файл.

### `planner.PlanInterruptions`

Функция принимает длительности клипа и баннера и проверяет, что обе конечны и
положительны.

Правила MVP:

```text
clip <= 90 секунд → одна вставка посередине
clip > 90 секунд  → вставки на 30, 60, 90, ... пока точка меньше clip duration
```

Точка, совпадающая с концом клипа, не создаётся: после неё не осталось бы
исходного кадра. Поэтому для 120 секунд точки равны `30, 60, 90`, а для 130 —
`30, 60, 90, 120`.

Длительность banner не захардкожена. `main` отдельно вызывает
`FFProbe.Probe(bannerPath)` и передаёт найденную длительность планировщику.

### Связывание этапов в `main`

`main` читает аргументы, одним экземпляром `FFProbe` анализирует source и
banner, вызывает `EqualSplit`, затем проходит по полученным клипам и добавляет
результат `PlanInterruptions`.

Последним шагом стандартный `encoding/json` печатает source metadata, banner
metadata и все планы. На любой ошибке программа пишет причину в stderr и
завершается с ненулевым кодом.

## Этап 4 — Single Clip Renderer

### `renderer.FFmpeg`

Структура содержит необязательное поле `Command`. Пустое значение означает
`ffmpeg` из системного `PATH`; явный путь можно будет передать через
конфигурацию на VPS без изменения бизнес-логики.

### `FFmpeg.Render`

Метод получает контекст, путь source, путь результата и один `ClipPlan`.

Перед запуском он проверяет:

- оба пути непустые;
- `Start` конечен и неотрицателен;
- `Duration` конечна и положительна.

`os.MkdirAll` создаёт родительский каталог результата. После этого
`exec.CommandContext` запускает FFmpeg напрямую, без shell. Поэтому пробелы и
специальные символы в путях остаются частью одного аргумента и не исполняются
как команды.

`CombinedOutput` нужен для понятной диагностики: при падении FFmpeg ошибка
содержит номер клипа и сообщение самого FFmpeg.

### `renderArgs`

Функция формирует аргументы отдельно от запуска процесса, благодаря чему
команду можно проверить быстрым unit-тестом без реального кодирования.

Параметры текущего этапа:

```text
-i source        открыть исходник
-ss Start        перейти к началу ClipPlan
-t Duration      взять заданную длительность
-map 0:v:0       взять первый видеопоток
-map 0:a:0?      взять аудио, если оно существует
-c:v libx264     кодировать видео в H.264
-preset medium   баланс скорости и сжатия
-crf 18          качественное изображение
-pix_fmt yuv420p совместимый пиксельный формат
-c:a aac         кодировать звук в AAC
-movflags +faststart перенести MP4 metadata в начало файла
```

Времена форматируются с точностью до микросекунды. `-ss` находится после
входного файла: на этом этапе выбран точный, хотя и более медленный seek.
Оптимизировать seek имеет смысл только после измерений на длинных исходниках.

### Проверка результата

После `Render` точка входа снова вызывает существующий `FFProbe.Probe`, но уже
для `storage/output/clip-001.mp4`. Поэтому успешный код возврата FFmpeg — не
единственная проверка: приложение также убеждается, что контейнер читается, и
возвращает его фактические duration, FPS, codecs и разрешение.

Фактическая длительность может отличаться от плана примерно на один кадр:
FFmpeg завершает поток на границе видеокадра, а аудио — на границе аудиофрейма.
Например, запрос `3.417` секунды для текущего 60 FPS source дал контейнер
`3.433333` секунды. Это ожидаемая дискретность, а не потеря части source.

Stage 4 не использует `Interruption[]`: его задача — отдельно доказать точную
нарезку одного фрагмента. Вставка banner появится на Stage 6.

## Этап 5 — TikTok video normalization

Вертикализация добавлена прямо в существующий `renderArgs`, поэтому отдельный
промежуточный MP4 не создаётся. Нарезка, преобразование кадра и кодирование
выполняются одним процессом FFmpeg.

### `split`

Видеопоток делится на две независимые ветки:

```text
source video
├── bgsrc → фон
└── fgsrc → основной кадр
```

Это не копирование файла: обе ветки существуют только внутри filter graph.

### Фоновая ветка

`crop` вырезает из центра source область с пропорциями `9:16`. Выражения с
`min` работают и для горизонтального, и для вертикального исходника. Затем
`scale=1080:1920` заполняет весь целевой кадр, `setsar=1` нормализует форму
пикселя, а `boxblur=20:1` размывает фон.

Crop выполняется до увеличения. Для горизонтального видео это заметно дешевле,
чем сначала растягивать весь широкий кадр до высоты 1920, а затем отрезать края.

### Основная ветка

`scale` вписывает исходное изображение внутрь `1080×1920` с
`force_original_aspect_ratio=decrease`. Поэтому изображение не растягивается и
не обрезается. `force_divisible_by=2` гарантирует чётные размеры, необходимые
для совместимого `yuv420p`.

### `overlay`

Основной кадр накладывается по центру размытого фона:

```text
x = (background width  - foreground width)  / 2
y = (background height - foreground height) / 2
```

Последний `format=yuv420p` закрепляет совместимый формат итогового потока. В
`-map [video]` передаётся результат filter graph, а аудио по-прежнему берётся
непосредственно из source.

Фильтр не задаёт новый `-r`, поэтому FFmpeg сохраняет временную сетку и FPS
исходного видеопотока. После рендера `FFProbe` проверяет, что результат имеет
разрешение `1080×1920` и ожидаемый FPS.

Один универсальный filter graph применяется к любой ориентации. Для видео,
которое уже точно соответствует `9:16`, foreground закрывает фон целиком; для
остальных форматов свободная область заполняется размытой копией.

На текущем горизонтальном source сквозная проверка дала `1080×1920`, 60 FPS,
H.264/AAC. Контрольный кадр подтверждает: foreground центрирован, его пропорции
сохранены, а свободные области сверху и снизу заняты blurred background.

## Этап 6 — Banner Renderer

Stage 6 расширяет тот же единственный FFmpeg filter graph. Промежуточные
`source clip`, `freeze` или `transparent banner` файлы не создаются.

### Новый контракт `FFmpeg.Render`

Метод получает:

```text
context
source path
banner path
output path
ClipPlan с готовыми Interruption[]
```

Renderer не проверяет длительность клипа по правилу `90 секунд` и не выбирает
точки `30/60/90`. Эти решения уже принял `PlanInterruptions`. Renderer только
исполняет переданный план.

### `validateClip`

До запуска FFmpeg проверяется:

- конечные и допустимые `Start`/`Duration` клипа;
- наличие хотя бы одной вставки;
- каждая точка находится строго внутри клипа;
- точки идут по возрастанию;
- длительность каждой вставки положительна и конечна.

Это не позволяет передать FFmpeg пересекающийся или бессмысленный план и
получить повреждённый результат без понятного сообщения.

### Подготовка source

`-ss` и `-t` ограничивают первый input нужным `ClipPlan`. Затем вертикальная
композиция Stage 5 становится потоком `[base]`.

`[base]` разделяется на:

- обычные source-сегменты до, между и после вставок;
- по одной ветке для freeze-frame каждой вставки.

Source audio отдельно делится на соответствующие аудиосегменты. Во время
banner source audio в concat вообще не участвует, поэтому это настоящая пауза,
а не приглушение продолжающего играть звука.

### Freeze-frame

Для каждой `Interruption.At` берётся первый source-кадр в этой точке. `tpad` с
`stop_mode=clone` повторяет его на `Interruption.Duration`, после чего `trim`
фиксирует точную длительность freeze-сегмента.

Исходный timestamp при этом не продвигается: source после banner начинается с
той же границы, на которой был остановлен.

### Chroma key и overlay

Banner video обрезается до фактической длительности, полученной через
`ffprobe`, и начинает timestamps с нуля. Фильтр:

```text
chromakey=0x00FF00:0.30:0.10
```

удаляет зелёный фон. Затем banner вписывается в `1080×1920` с сохранением
aspect ratio и накладывается по центру freeze-frame.

Текущий banner очень широкий (`1280×496`). При сохранении пропорций и полном
размещении внутри `1080×1920` его максимальная площадь составляет около 22%
кадра. Одновременно выполнить требования «не обрезать», «не деформировать»,
«не выходить за кадр» и «занимать 45% площади» для такого aspect ratio
геометрически невозможно. Используется ранее визуально одобренный вариант на
полную ширину. Если 45% станет обязательным, понадобится отдельный crop/layout
баннера или другой исходный artwork.

### Banner audio и concat

Banner audio нормализуется до stereo/48 kHz. Source и banner сегменты
чередуются:

```text
source before
→ banner video + banner audio
→ source after
```

Для нескольких точек схема строится динамически:

```text
source #0 → banner #0 → source #1 → banner #1 → ... → source #N
```

Видео- и аудиоцепочки склеиваются отдельными `concat`, а затем кодируются в
H.264/AAC. Готовая длительность равна:

```text
clip.Duration + сумма interruption.Duration
```

### Проверка Stage 6

Для текущего клипа ожидаемая длительность была:

```text
3.417 + 3.833333 = 7.250333 секунды
```

`ffprobe` получил `7.25` секунды, `1080×1920`, 60 FPS, H.264/AAC. Контрольные
кадры до, во время и после вставки подтвердили freeze-frame, прозрачный зелёный
фон, центральный overlay и продолжение source.

Дополнительный integration test программно создаёт маленькие source/banner,
рендерит две вставки и проверяет результирующую длительность. Если FFmpeg не
установлен, этот тест корректно пропускается.

## Минимальный Debug UI

Интерфейс намеренно реализован стандартной библиотекой Go. Нет Node.js, npm,
React, сборщика frontend или отдельного JSON API: для текущей задачи они не
дают дополнительной пользы.

После первой визуальной проверки интерфейс дополнительно упрощён: удалены
логотипный блок, декоративные статусы, градиенты, карточки метрик, пустой экран
и поясняющие подписи. Остались только форма, одна строка метаданных, video,
таблица плана и JSON.

### `factory.Result` и `factory.Run`

Рабочая последовательность раньше находилась непосредственно в CLI. После
появления второго клиента она вынесена в одну общую функцию:

```go
Run(ctx, sourcePath, bannerPath, outputPath, parts) (Result, error)
```

Функция последовательно запускает Media Probe, Equal Split Planner и
Interruption Planner. Затем она проходит по всем `ClipPlan`, для каждого
запускает FFmpeg Renderer и повторный Media Probe результата.
CLI только разбирает аргументы и кодирует `Result` в JSON; web handler только
проверяет форму и отображает тот же `Result`.

### Имена выходных файлов

Четвёртый аргумент CLI — имя первого результата. При значении по умолчанию
файлы называются:

```text
storage/output/clip-001.mp4
storage/output/clip-002.mp4
...
storage/output/clip-NNN.mp4
```

`numberedOutputPath` сохраняет директорию и расширение, удаляет у основы
суффикс `-001` и добавляет трёхзначный номер. Первый путь оставляется ровно
таким, каким его передал пользователь. Рендер выполняется последовательно:
так проще контролировать нагрузку CPU и памяти на локальном Mac и небольшом
VPS. Параллельный worker pool понадобится только после реального измерения
времени и ресурсов.

Если FFmpeg или последующий `ffprobe` падает, `Run` возвращает номер проблемного
клипа. Уже готовые предыдущие файлы остаются на диске и не теряются.

### `cmd/web/main.go`

Сервер слушает `127.0.0.1:8080`, поэтому по умолчанию доступен только локально.
Адрес можно заменить переменной `CONTENT_FACTORY_ADDR`.

Маршруты:

```text
GET  /                       форма и пустое состояние
POST /render                 запуск полного batch pipeline
GET  /output/{name}          video preview выбранного результата
```

HTML встроен в Go binary через `go:embed`, поэтому на другом компьютере не
нужно отдельно искать директорию со статическими файлами.

### Выбор медиафайлов

`mediaFiles` показывает только существующие `.mp4` из `storage/incoming`.
`resolveMedia` запрещает пустые имена, абсолютные пути, `../` и другие попытки
выйти из этой директории, затем проверяет, что цель является обычным файлом.
Относительные symlink текущего проекта корректно проходят `os.Stat`.

Количество частей принимается только в диапазоне `1..1000`. Это защита
локального debug-инструмента от случайного создания огромного плана.

### Выполнение рендера

POST остаётся открытым до окончания FFmpeg. Контекст HTTP-запроса передаётся в
pipeline, поэтому отменённый запрос останавливает внешний процесс. `sync.Mutex`
не позволяет двум вкладкам одновременно перезаписывать один debug output.

После успеха страница показывает:

- отдельный блок каждого результата с путём, разрешением, FPS и duration;
- отдельный `<video controls>` для каждого готового клипа;
- таблицу всех `ClipPlan` и точек banner;
- полный JSON в раскрываемом блоке.

К URL видео добавляется уникальный query-параметр, а endpoint отвечает с
`Cache-Control: no-store`, поэтому браузер не показывает предыдущий рендер из
кэша.

## Что проверяют тесты

Media Probe:

- video/audio codecs и наличие потоков;
- разрешение и длительность;
- дробный FPS;
- fallback на `r_frame_rate`;
- ошибки некорректной длительности и FPS.

Equal Split:

- нужное количество клипов;
- последовательную нумерацию;
- отсутствие промежутков и пересечений;
- точное использование конца source;
- отклонение некорректных аргументов.

Interruption Planner:

- граничные длительности 30, 60, 89, 90, 91, 120, 130 и 180 секунд;
- одинаковую длительность banner во всех вставках;
- отклонение нулевых, отрицательных, бесконечных и `NaN` значений.

Single Clip Renderer:

- точный порядок аргументов FFmpeg;
- форматирование времён;
- сохранение пути с пробелами одним аргументом;
- сквозной рендер реального первого клипа и его повторный `ffprobe`.

TikTok normalization:

- наличие полного filter graph в аргументах FFmpeg;
- единый аргумент filter graph без участия shell;
- сквозная проверка разрешения `1080×1920` и FPS через `ffprobe`;
- визуальная проверка кадра из готового MP4.

Banner Renderer:

- валидация позиций, порядка и длительностей вставок;
- chroma key, freeze-frame и source/banner audio в filter graph;
- схема concat для одной и четырёх вставок;
- реальный integration render с двумя вставками;
- длительность и метаданные реального результата;
- визуальные кадры до, во время и после banner.

Debug UI:

- отклонение path traversal и файлов не-MP4;
- список только допустимых файлов;
- сборка и `go vet` обоих entrypoints;
- HTTP GET страницы и POST реального рендера;
- визуальная проверка desktop layout и video preview.

Batch pipeline:

- первый output сохраняет переданный путь;
- последующие outputs получают номера `-002`, `-003` и далее;
- CLI и debug UI получают один и тот же список `factory.Result.Outputs`;
- каждый готовый файл повторно проверяется через `ffprobe`.

## Переносимость macOS → Linux/VPS

В коде нет абсолютных пользовательских путей. Go вызывает `ffprobe` и `ffmpeg` через
`PATH`, работает с относительными путями проекта и использует только стандартную
библиотеку. На VPS достаточно установить Go и FFmpeg и перенести каталог.

## Следующий этап

Следующий полезный этап — удобство длительных запусков:

1. показывать текущий номер клипа во время batch;
2. разрешить повторить только упавший клип;
3. добавить очередь только если один синхронный локальный рендер станет
   реальным ограничением.

Отдельный `RenderPlan` и worker pool пока намеренно не добавлены: текущих
`ClipPlan[]` и последовательного цикла достаточно для работающего batch.
